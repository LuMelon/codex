# 计划：CodeX 阅读 RTL 仓库并生成系统级测试激励的上下文管理与方法论调研

## Summary

本次执行阶段的目标不是修改当前仓库代码，而是产出一份面向芯片 RTL/验证场景的分析答复，帮助用户回答以下问题：

1. 当 RTL 仓库级上下文非常大时，如何让 CodeX 有效理解设计并生成测试激励。
2. 当激励最终采用系统级 `C` 代码/裸机固件形式时，如何保证激励“合法”，避免生成违反协议、寄存器约束或系统初始化顺序的刺激。
3. 当用户给的是“针对核的激励”时，如何把它映射到仓库中某些特定模块、状态机、总线链路、DMA/中断路径等内部对象上。
4. 有哪些值得参考的研究和工程模式，可以作为方法论和后续落地工作流的基础。

执行阶段应输出三部分内容，顺序固定：

1. 论文/方案调研综述
2. 方法论方案
3. 落地工作流建议

答复语言使用中文，定位为“给思路、给框架、给落地路线”，而不是绑定当前工作区的具体实现。

## Current State Analysis

### 用户意图与已确认边界

- 用户要解决的是真实 RTL/芯片验证场景，不一定与当前工作区代码仓库相关。
- 用户希望最终拿到三部分内容：先调研综述，再方法论方案，最后再讨论怎么落地工作流。
- 目标对象既包括单个 IP 核，也包括更大的 SoC 子系统。
- 生成的测试激励不只是一类：
  - 早期提到过序列级/场景级和原始向量级。
  - 用户进一步明确，更关心系统级 `C` 语言形式的软件测试激励。
- 目标执行环境以裸机/固件为主。
- 后续希望把覆盖率、波形和失败信息统一纳入闭环。

### 当前工作区探索结果

- 当前 `/workspace` 中是 `codex`/`codex-rs` 相关仓库，没有现成的 RTL 设计仓库可直接分析。
- 用 HDL 关键词扫描 `/workspace`，未发现可直接作为样例的 `SystemVerilog/Verilog/VHDL` 设计代码。
- 因此本次计划必须定位为“通用方案设计 + 文献与工程模式调研”，不能假装基于当前仓库做 RTL 级实施细化。

### 已完成的外部调研与可借鉴方向

已读/已检索的代表性材料与关键信号：

- `UVMarvel`：
  - 关键词：`IR`、`Bus Protocol Library`、`Coverage Analyser`、`Signal Tracker`、`Verilog Patching`、`LLM-Guided Sequence Execution`
  - 对本题的启发：
    - 不能把完整子系统 RTL 一次性交给 LLM，而应先转成验证导向的中间表示。
    - 覆盖率提升不是盲目再生成激励，而是先做“未覆盖点 -> 信号路径 -> 精简上下文 -> 新激励”的闭环。
    - 对“如何触发到特定模块”尤其有参考价值，说明应先构建信号/依赖路径而不是直接凭自然语言猜测。
- `HAVEN`：
  - 关键词：`Hybrid`、`Template Engine`、`Protocol-Aware DSL`、`coverage gap reports`
  - 对本题的启发：
    - 不能让 LLM 直接自由发挥去写大量 HDL/UVM/协议刺激。
    - 应用受约束的模板、协议 DSL、规则生成器来保证“合法性”。
    - 对用户担心的“生成信号是否合法”问题，有直接借鉴意义。
- `LLM Wiki / Search-First` 类设计：
  - 关键词：`search-first`、`knowledge pages`、`token budget management`
  - 对本题的启发：
    - 仓库级大上下文不应依赖单次 prompt 全量注入。
    - 应建设分层知识库或结构化索引，优先检索，再拼装小上下文。
- `FireBridge` 和 HW/SW co-verification 方向：
  - 关键词：`hardware + firmware co-verification`、`production firmware`、`register-level protocol testing`
  - 对本题的启发：
    - 如果激励最终是裸机/固件 `C` 程序，最自然的触发路径是“软件动作 -> 寄存器/内存映射/中断/DMA -> 总线事务 -> 内部模块状态变化”。
    - 这条链路天然比直接生成底层 pin toggle 更适合控制合法性。

### 关键约束与结论

- 约束 1：仓库级 RTL 上下文可能远超 LLM 窗口，必须采用分层上下文管理。
- 约束 2：用户的激励目标是系统级 `C` 软件，因此必须强调“软件可见抽象”而非只停留在 RTL 信号层。
- 约束 3：用户希望覆盖率、波形和失败信息全部入环，因此方案必须包含反馈闭环，而不是单次生成。
- 约束 4：用户的核心痛点不只是“生成激励”，更是“如何知道该激励能到达哪个模块、是否合法、为什么能触发”。

## Proposed Changes

执行阶段需要产出的不是代码修改，而是一份结构化答复。答复必须分成以下几个部分，并覆盖指定论点。

### 1. 调研综述部分

目标：

- 对用户说明目前可借鉴的研究脉络是什么。
- 不是泛泛而谈 LLM for HDL，而是围绕“仓库级上下文管理”“合法激励生成”“模块级触达”“闭环优化”组织。

必须包含的内容：

- `UVMarvel`、`HAVEN`、`HW/SW co-verification`、`search-first / knowledge-base` 四类方向的核心思想。
- 每类方案回答什么问题、解决了什么痛点、仍然有哪些局限。
- 明确指出：现有很多工作停留在 IP/UVM 自动生成层，而用户的问题更偏“仓库级理解 + 软件驱动的硬件触达”。

建议结构：

1. 为什么 RTL 仓库级任务比单个函数/单模块代码理解难得多
2. 学术/工程上常见的四条路线
3. 哪些方法适合直接迁移到用户场景
4. 哪些地方现成工作还不够，需要自建能力

### 2. 方法论方案部分

目标：

- 给出一套“如果我是你，我会怎么搭这个系统”的方案。
- 重点解决上下文管理、合法性控制、路径触达、闭环优化四个问题。

必须明确提出的架构分层：

#### 2.1 仓库理解层

说明应把 RTL 仓库预处理成多层知识表示，而不是把原始源码全文喂给 LLM：

- 层 A：仓库级索引
  - module/interface/package/include 层级
  - 文件到模块映射
  - 实例化关系
  - 寄存器定义与地址映射
  - 总线/时钟/复位/中断/DMA 拓扑
- 层 B：模块级摘要卡片
  - 模块职责
  - 上下游接口
  - 关键寄存器/状态机
  - 可观察信号
  - 可触发入口
  - 依赖前置条件
- 层 C：路径级切片
  - 从“软件动作”到“模块状态变化”的因果链
  - 例如：CPU 写寄存器 -> interconnect -> target IP control reg -> FSM state -> submodule enable -> internal event
- 层 D：验证知识层
  - 已知约束
  - 覆盖点
  - 失败模式
  - 常见 bug 触发模式

需要强调的关键思想：

- CodeX 的上下文管理应采用“搜索优先 + 局部切片 + 分层摘要 + 闭环记忆”，而不是“全仓库一次性读完”。
- 对每个任务只取足够小的一段上下文：
  - 任务是“找某模块触发路径”时，拿路径相关模块和寄存器映射。
  - 任务是“补某覆盖空洞”时，拿覆盖点、相关信号锥、上次失败日志和可用软件入口。

#### 2.2 合法性控制层

此部分必须直接回应用户的核心担忧：“我没有办法保证它生成的信号一定合法”。

需要明确给出结论：

- 不建议让 LLM 直接自由生成任意底层信号刺激作为主路径。
- 主路径应升级为“软件可见动作 DSL / API / 模板化驱动调用”。

必须提出的合法性手段：

1. 用软件动作而不是原始信号作为生成原语
   - 如：寄存器写、descriptor 构造、buffer 布局、中断使能、poll/timeout、DMA 提交、cache flush、doorbell、reset sequence
2. 用协议/寄存器规则约束生成空间
   - 地址范围、bitfield 合法值、写前读后顺序、使能依赖、状态机前置条件
3. 用模板和 DSL 兜底
   - LLM 只生成高层测试意图或参数
   - 真正的 `C` 激励代码由模板/代码生成器输出
4. 用静态检查 + 动态检查双重过滤
   - 静态：寄存器字段合法性、调用顺序、资源初始化完整性
   - 动态：断言、协议 checker、非法访问 trap、软件返回码、日志检查
5. 必要时保留“小范围信号级注入”作为辅助手段而不是主路径
   - 只用于某些软件无法自然触及的异常场景
   - 且要显式标注为“非自然激励”或“故障注入”

#### 2.3 目标模块触达层

此部分必须回答“我给的是核级激励，怎么去触发到某些特定模块上”。

需要明确提出一种“目标可达性分析”思路：

1. 从目标模块反向推导其可观察/可控制入口
   - 哪些寄存器、总线事务、DMA 通道、中断、时钟门控、配置状态会影响它
2. 建立“软件动作 -> 事务 -> RTL 路径 -> 目标模块”的映射图
3. 为每个目标模块维护一个 `activation recipe`
   - 前置初始化
   - 最短触达路径
   - 常见增强路径
   - 需要的外设/内存环境
   - 成功触达的证据
4. 对复杂模块使用 `cone-of-influence`/依赖切片
   - 只把与该模块触发相关的子图交给 LLM
5. 把“能不能触发到”从猜测问题变成可验证问题
   - 通过覆盖点、关键波形模式、断言、日志 signature 判断是否真正到达

执行阶段必须给出至少一个具体例子模板，例如：

- “为了触发某个 DMA 子模块，系统级 `C` 激励不直接写内部信号，而是完成 buffer 准备、寄存器配置、doorbell 提交、等待中断，再用波形/coverage 验证 DMA engine、arbiter、descriptor fetch 和 target datapath 是否被命中。”

#### 2.4 闭环优化层

必须给出“生成后如何不断变好”的闭环：

1. 初始生成
   - 基于模块摘要、寄存器模型、软件入口和覆盖目标生成测试意图
2. 执行采样
   - 跑仿真/协同验证，收集覆盖率、波形摘要、失败信息
3. 差距归因
   - 哪些覆盖点没打到
   - 卡在哪个路径节点
   - 是初始化不完整、约束不合法、还是环境依赖不满足
4. 定向修正
   - 修改软件动作序列、参数组合、内存布局、并发时序
5. 经验沉淀
   - 把成功 recipe 和失败 pattern 存成知识页，供后续检索复用

要强调：

- 闭环输入不应把全波形全文送给 LLM。
- 应先做结构化提炼，再喂给 CodeX：
  - 覆盖空洞列表
  - 关键状态转移摘要
  - 断言/错误日志
  - 路径命中与否

### 3. 落地工作流建议部分

目标：

- 给用户一条现实可执行的演进路线，而不是一次性要求建设完整平台。

建议按阶段写：

#### Phase 0：手工辅助阶段

- 先建立最小知识底座：
  - 模块树
  - 实例图
  - 寄存器地图
  - 关键模块 activation recipe
- 让 CodeX 先只做：
  - 查询模块作用
  - 解释从软件到模块的路径
  - 起草测试意图

#### Phase 1：受约束生成阶段

- 引入软件刺激 DSL / 模板化 `C` 代码生成
- LLM 只输出：
  - 测试目标
  - 参数
  - 场景组合
  - 预期命中模块
  - 预期覆盖点

#### Phase 2：反馈闭环阶段

- 把覆盖率、失败日志、波形摘要接回来
- 做 coverage gap triage
- 定向补激励

#### Phase 3：仓库级知识化阶段

- 建立可搜索的 RTL wiki / recipe 库 / bug pattern 库
- 把一次次验证经验变成后续任务的先验

#### Phase 4：局部自动化阶段

- 对高价值模块先自动化
- 不追求一开始覆盖整个 SoC
- 优先选择寄存器可控、路径清晰、反馈好量化的模块

### 4. 明确的答复立场

执行阶段需要明确表达以下观点：

- 真正的难点不是“让 LLM 看更多代码”，而是“把仓库知识压缩成任务相关的结构化上下文”。
- 对芯片验证来说，上下文管理的核心单位不应该是文件，而应该是：
  - 模块
  - 接口/协议
  - 寄存器
  - 依赖路径
  - 覆盖点
  - 触发 recipe
- 为保证合法性，生成粒度应尽量提升到软件动作/事务级，而不是自由信号级。
- “从核触发模块”本质上是一个可达性/因果链分析问题，不只是 prompt engineering 问题。
- 最有价值的系统不是一次生成最强，而是能把覆盖率、波形和失败信息持续回灌的系统。

## Assumptions & Decisions

### Assumptions

- 用户当前最需要的是方法与路线，不是针对某个具体 RTL 仓库的即时实现。
- 用户未来可能会把这套思路用于多个不同规模的设计，包括单 IP 和 SoC 子系统。
- 用户能接受“先把问题变成受约束生成 + 反馈闭环”，而不是追求完全自由的端到端自动生成。

### Decisions

- 采用“研究综述 -> 方法论 -> 落地路线”的最终答复结构。
- 以系统级 `C`/裸机固件激励为主线来组织答案。
- 将“合法性控制”作为核心章节，而不是附带说明。
- 将“目标模块触达”明确建模为：
  - 结构分析问题
  - 路径追踪问题
  - 可验证问题
- 调研材料只作为支撑，不把最终答案写成论文笔记；必须转化成用户可操作的方法建议。
